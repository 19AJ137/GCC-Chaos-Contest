# GCC6 の仕様（Gcc6_32.dll から復元したアルゴリズム）

GCC カオス暗号の懸賞の暗号文は、GCC6 の DLL の `File_cryption` で作られています。この文書は、32bit 版の `Gcc6_32.dll`（1997-01-23 ビルド）を逆アセンブルして復元したアルゴリズムの仕様です。

- 参照実装: [`../src/gcc6/gcc.py`](../src/gcc6/gcc.py)。この文書と食い違うときは `gcc.py` が正しい。
- 実物との一致: `gcc.py` は、実物の DLL を Unicorn で動かした出力と `Str_cryption` で 600/600、`File_cryption` で 60/60 が一致する（[`../src/gcc6/test_vs_emu.py`](../src/gcc6/test_vs_emu.py)・[`test_file.py`](../src/gcc6/test_file.py)）。C の移植（[`gccfast.h`](../src/gcc6/gccfast.h)）とも 5,000 鍵で一致。
- DLL は [`../../software/`](../../software/) の配布物の中にある。取り出し方は [`../src/README.md`](../src/README.md)。

語 = 4 バイト。数値の 16 進は、特に断らない限り倍精度（IEEE 754）のビット列。

---

## 1. 入口

| 関数 | 引数 | 備考 |
|---|---|---|
| `Str_cryption(mode, in, len, out, key)` | mode 1 = 暗号化、2 = 復号。len は 16 ビット | メモリ上のバッファを処理する |
| `File_cryption(mode, infile, outfile, key)` | 同上 | 1,024 バイトのブロック単位（§6）。ヘッダなし、出力の長さ = 入力の長さ、詰め物なし。成功で −1（VB の True） |

- 鍵は 1〜40 バイトのバイト列。アプリ（インフォガード、`INFGD.EXE`）は入力欄の文字列を ANSI（日本語 Windows では Shift_JIS）にしてそのまま渡す（前後の空白も削らない）。日本語版のヘルプには漢字も使えると書いてある。
- アプリの「暗号化」はモード 1、「復号化」はモード 2（どの版も同じ）。
- 1,024 バイト以下のデータでは、`File_cryption` と `Str_cryption` は同じ出力になる。

## 3. 鍵スケジュール

鍵から、写像の初期値・定数のもと・連鎖の初期値などを作る。**このあと鍵そのものは使わない。**

```
k780 = k788 = k7b0 = k7b8 = 1.0;  S = T = 0（32 ビットで回り込む）
鍵を 4 バイトずつ、リトルエンディアンの符号なし整数 c にする（最後の塊の足りない分は 0 で埋める）。塊ごとに:
  clr(x)  = 倍精度の最下位バイト（仮数の下位 8 ビット）を 0 にする
  f1, i1 = modf(clr(c  * K_PI));   f2, i2 = modf(clr(i1 * K_PI))
  f3, i3 = modf(clr(c  * K_E ));   f4, i4 = modf(clr(i3 * K_E ))
  k780 *= (1 + f1);  k788 *= (1 + f2);  k7b0 *= (1 + f3);  k7b8 *= (1 + f4)
  S += ftol(i3 / i2) + ftol(i1);    T += ftol(i1 / i4) + ftol(i3)
     ftol = MSVC の _ftol（fistp qword で切り捨て、下位 32 ビット）。inf・NaN・|x| ≥ 2^63 は 0
k780・k788・k7b0・k7b8 のそれぞれについて: 1 より大きければ、小数部だけを残し、整数部を S に足す
warm = max(S mod 79, 11)                 … 空回しの回数（11〜78）
b0, b1 = T の下位 2 バイト               … 状態と定数の下位 16 ビットに毎回書き込む値（以下 lo とも書く）
写像の番号 m = (最後の塊の i2 を 32767 以下になるまで 0.1 倍した値を ftol し、int16 にしたもの) mod 3
              （剰余は被除数の符号。負になると写像が初期化されない）
IV = S                                   … 連鎖レジスタの初期値（4 バイト、リトルエンディアン）
写像の初期化（§4）のあと、warm 回だけ写像を進める（空回し）
```

- 変数の名前（k780 など）は、DLL の中の番地から取ったもの。
- 鍵の塊の順序を入れ替えても、最後の塊（写像の番号を決める）が同じなら、同じ内部状態になることが多い（積と和しか使わないため。違いは積を掛ける順序による丸めだけ）。懸賞の鍵 k でも、先頭 3 塊の並べ替え 6 通りが同じ鍵ストリームを出す。
- 鍵スケジュールの出力のうち、鍵ストリームに効くのは m、k780・k788（初期値）、k7b0・k7b8（定数のもと）、S（IV と空回し）、b0・b1 だけ。

## 4. 写像

倍精度の数の列を作る 3 種類の「カオス写像」。**毎回の更新のあと、状態の倍精度の下位 16 ビットを (b0, b1) で上書きする。** 初期化のときも、定数（r、Q、A、C）の下位 16 ビットを (b0, b1) で上書きする。

| m | 更新 | 定数と初期値 | 出力 |
|---|---|---|---|
| 0 | x ← (1 − x)·x·r | x₀ = k780（0.5 または 0 以下なら X0_DEF）、r = k7b0·0.1000…09 + 3.9 ∈ [3.9, 4.0) | x |
| 1 | y ← y² − p | y₀ = 2·k780 − 1（下位 16 ビットも上書き）、p = k7b0·0.1000…09 + 1.9 ∈ [1.9, 2.0) | (1 + y)/2 |
| 2 | a = Q·u; b = a·u; u ← A·u − a·v; v ← C·v + b | u₀ = k780、v₀ = k788、P = 0.4·k7b0 + 0.9、Q = (−0.14·k7b8 − 0.8·P) + 1.72、A = Q·P + 1、C = 1 − Q | v |

- 計算の順序は上の式のとおり（`gcc.py` の `step()`・`setup_map()`）。順序を変えると丸めが変わり、鍵ストリームがずれる。
- 写像 2 で (u, v) → (−u, v) は同じ v の軌道になる。u の符号は出力から観測できない。
- 写像 2 の (Q, A) の範囲: P = (A − 1)/Q ∈ [0.9, 1.3]、0.8P + Q ∈ [1.58, 1.72]。
- **NaN の弱い鍵**: 写像 2 で軌道が発散する鍵では、鍵ストリームが 0 になり、暗号文が平文と同じになる（例: `9678929`・`3129929`。短い数字・英数字の鍵の 0.03〜0.05%）。

## 5. 暗号化の内側ループ（`Str_cryption`・`File_cryption` 共通）

```
chain = IV（4 バイト）;  bl = IV の 2 バイト目（IV[1]）
4 バイトごとに:
  写像を 1 歩進め、出力の倍精度のバイト列 z[0..7]（リトルエンディアン）を取る
  ks = (z[4], z[2], z[3], z[5])            … 鍵ストリームの語（仮数のビット 16〜47）
  z[6] > 0xE6 なら（連鎖なし）:  C = P ⊕ ks
  そうでなければ（連鎖あり）:    C = P ⊕ ks ⊕ chain
                                  chain = C（暗号化のとき）／ chain = 入力（復号のとき）
4 バイトに満たない端数（1〜3 バイト）: 写像をもう 1 歩進めて ks を取り、バイトごとに
  C[j] = P[j] ⊕ ks[j] ⊕ bl;  bl = C[j]（暗号化）／ 入力（復号）
```

- 連鎖するかどうかは、平文によらず、写像の出力の大きさだけで決まる。連鎖なしは |出力| ∈ [0.71875·2^(16j), 2^(16j+1))（j ≤ 0。実際にはほぼ j = 0 の [0.71875, 2)）。写像 2 では、連鎖ありが約 77%。
- 鍵ストリームの語は、写像の出力の仮数 32 ビットそのもの。出力のうち鍵ストリームに出ないのは、下位 16 ビット（b0・b1 で固定）と上位 16 ビット（符号・指数・仮数の上位 4 ビット）だけ。
- 復号（モード 2）は、連鎖レジスタに入力（暗号文）を入れる。暗号化と復号は互いに逆で、どちらの順にかけても元に戻る（D(E(P)) = P、E(D(P)) = P）。
- ナンスも乱数の IV もない。同じ鍵なら、どのファイルでも同じ鍵ストリーム・同じ連鎖フラグになる。

## 6. `File_cryption` のブロック処理

- 1,024 バイトごとに §5 のループを回す。chain と bl は次のブロックに引き継ぐ。
- 各ブロックのあと、**k7b0（鍵スケジュール直後の値）のバイト 5 を chain のバイト 1 に置き換えて**定数を作り直し、**写像を初期値に戻す**（§4 の初期化をやり直す。空回しはしない）。
- したがって、1,024 バイト以下のファイルは `Str_cryption` と同じ出力になる。懸賞の A・B（1,024 バイト）は 1 ブロックだけ、E（1,338 バイト）は 2 ブロック目（314 バイト）が別の鍵ストリームになる。

## 7. 実装の注意（計算の再現性）

- 32bit 版の DLL は、C ランタイムの初期化で x87 の精度を 53 ビットにしている。どの環境でも IEEE 倍精度の計算と同じ結果になる（Python の float と一致する）。Unicorn で動かすときも、FPU の制御語を 0x027F にする（`emu.py`）。
- **C で書くときは FMA の縮約を禁止する**（`-ffp-contract=off -fno-fast-math`。CUDA は `--fmad=false`）。演算の順序が DLL と変わると鍵ストリームがずれる。
- `ftol` は MSVC の `_ftol`（切り捨て、下位 32 ビット）。inf・NaN・範囲外は 0。0 での割り算は inf・NaN になってから `ftol` される（`gcc.py` の `fdiv`）。
- **16bit 版の DLL**（`gcc6.dll`、1996-09-02）は、同じアルゴリズムだが、拡張精度のまま計算する箇所が残っている。16bit DLL を精度 64 ビットで動かすと、0.551% の鍵（写像 2 では 1.370%）で鍵ストリームが 32bit 版とずれる（精度 53 ビットなら 0.053%）。懸賞の A・E は 16bit 版で作られたが、懸賞の 2 本の鍵では、精度によるずれは起きていない（32bit 版と同じ計算で全バイト再現できる）。鍵の候補を 16bit 版で確かめるときは、制御語 0x37F（64 ビット）と 0x27F（53 ビット）の両方で試す（[`../src/gcc6/emu16f.py`](../src/gcc6/emu16f.py)）。

## 9. 攻撃から見た性質

解読に効いた性質は [writeup.md](writeup.md) の §2.6 と §14、鍵（パスワード）の逆算に効いた性質は [password.md](password.md) の §1〜§4 にまとめた。要点だけ挙げる。

1. ナンスがなく、同じ鍵の暗号文どうしの XOR から鍵ストリームが消える。
2. 鍵ストリームの語は写像の状態（出力の仮数）そのもので、隠れているのは上位 16 ビットだけ。数語の鍵ストリームから、写像の定数と状態が倍精度の値として決まる。
3. 連鎖するかどうかは出力の値だけで決まり、平文が ASCII の区間では、暗号文の XOR の最上位ビットに現れる。
4. 鍵を使うのは鍵スケジュールだけ。§3 の出力が分かれば、鍵がなくても暗号化・復号ができる。
5. 鍵スケジュールは、塊ごとの小数部の積（k780 など）と整数部の和（S・T）だけでできている。clr で仮数の下位 8 ビットを消すので、小数部は粗い格子の上に乗る。積と和の連立として、鍵の塊を逆算できる（[password.md](password.md)）。
